01这是什么

一句话：给 AI 配一个「数据库总台」。

AI 想查数据库的时候，不直接连库，而是先找总台。总台负责：认出这是哪个库、判断这个操作允不允许、把请求转给对应的库、最后记一笔台账。

对这个 AI 来说，它眼里只有一个接口。背后是 MySQL 还是 Redis、在本地还是云端，它不用关心。

为什么叫 omni

omni = 全能、通吃。这个名字要表达三件事：

特质含义
通用不是「MySQL 工具」，而是能接各种类型的数据库
可扩展想支持一种新库，加一个插件文件就行，底座不用动
入口所有请求从这一个口进，由它分流

这套设计成立的核心证据

首版要接的 3 个库跨了三种完全不同的类型（关系型 / 键值型 / 文档型），它们的操作方式毫无共同点。如果连这三种都能用同一套契约接进来，说明这套抽象是真的成立。

02为什么需要它

先看没有它会怎样。

现状：每接一个库，就要配一遍

痛点具体表现
重复配置每个库一个 MCP 服务，地址、账号、密码重配一遍；3 个环境配 3 次
管不住没有统一的地方能说「这个库只能读，那个库能写」
没台账AI 到底执行过什么，事后无从查证
生产库不敢碰怕 AI 手一抖在云上删了数据，干脆不给它连
版本差异烦MySQL 5.7 和 8.0 语法不一样，AI 容易写出 5.7 跑不了的语句

有了它之后

方面变化
配置所有连接写在一处，一类库一个配置文件
管控三级权限 + 规则包，生产库锁死只读
审计每次操作自动落日志，含被拒绝的操作
扩展加新库 = 加一个插件文件 + 一个配置文件
版本差异连上后自动探测版本，按实际能力调整行为

03一个入口，两级分流

整个系统只有一张骨架图，看懂了这张就看懂了全部。

关键设计：一级分流那层，代码里不许出现 if mysql

一级分流只认两样东西：工具名和连接别名。它不知道 MySQL 是什么，也不知道 SQL 长什么样。所有数据库的细节都关在插件里。这条守住了，加新库就永远不用动底座。

扩展性验证：加一个库要动多少

想加什么要动的文件底座改动
支持 PostgreSQL新增 pgPlugin.py + pgConfig.yaml，base.py 加一行 import1 行
加一条危险规则一处 add_rule() 调用0
出错时发通知一处 on_error() 注册0
日志改落文件一处 set_backend()0
加一个 AI 工具工具面加个注册0

04三个角色

整个项目只有三种东西，职责边界很清楚。

底座

basePlugin.py + core/

入口、分流、规则、分级、审计、错误处理。
不认识任何数据库。

插件

plugins/*.py

连库、执行、探测版本、判断操作级别。
一个数据库类型一个文件，一个类。

连接配置

conf/*.yaml

有哪些库、在哪、什么级别。
密码不写在这，走环境变量。

规则包

rules/*.yaml

一套可复用的安全规则，可以全局套，也可以挂到单个连接。
纯规则，可放心分享。

一个库只对应一个类

MySQL 只有一个 MySQLPlugin 类，不管它是 5.7 还是 8.0、在本地还是云端。

版本差异不靠"多写几个类"解决，而是连上之后探测一次版本，把差异记在连接对象上，后面按实际情况调整行为。

05走一遍真实流程

用你自己的三个环境，看四件典型的事分别会发生什么。

一次调用的完整路径

场景 A · 查云端 CRM 的订单表（成功）

# AI 发起
db_query(connection="crm-prod", operation="SELECT id, amount, created_at FROM orders WHERE status='paid' LIMIT 50")

# 底座内部做的事
1. 一级分流       → 这是查询，走执行链路
2. 规则合成       → 加载 prod-safe 规则包：最高只读、最多 100 行
3. 分级判定       → SELECT 属于 L1 只读，连接上限也是只读 → 放行
4. 二级分流       → crm-prod → MySQLPlugin 实例（存活检查通过）
5. 插件执行       → 探测过版本是 5.7.43，无 CTE 能力；SQL 没用到，正常执行
6. 写审计日志     → 记录：谁、什么时候、哪个库、什么语句、多少行、耗时
7. 返回

# AI 收到
{
  "ok": true,
  "columns": ["id", "amount", "created_at"],
  "rows": [["10231", "5800.00", "2026-09-12 10:23:01"], ...],
  "row_count": 23,
  "elapsed_ms": 18,
  "truncated": false
}

场景 B · AI 想在云库删数据（被拦住）

# AI 发起
db_exec(connection="crm-prod", operation="DELETE FROM orders WHERE status='cancelled'")

# 底座内部做的事
1. 规则合成       → crm-prod 挂的是 prod-safe：max_level = readonly
2. 分级判定       → DELETE 属于 L2 写入，超过上限 readonly
3. 拦截          → 不执行，直接拒绝
4. 写审计日志     → 状态记为 denied（被拒的操作也要记！）

# AI 收到
{
  "ok": false,
  "error": "该操作需要 write 级别，连接 crm-prod 的上限是 readonly",
  "suggestion": "如需执行，请确认后在 conf/mysqlConfig.yaml 调整该连接的 level"
}

注意最后那条 suggestion——拒绝要拒绝得清楚，告诉 AI 为什么不行、以及怎么才能行。含糊的拒绝会让 AI 反复乱试。

场景 C · 从 Redis 取缓存（同一个工具，不同的库）

# AI 发起——注意 operation 的写法变了，但没有 SQL
db_query(connection="vm-docker-redis", operation="GET user:10086:session")

# 底座内部做的事
1. 一级分流       → 还是走执行链路（AI 用的还是同一个工具）
2. 规则合成       → 这个连接没挂额外规则包，用内置默认
3. 分级判定       → MySQL 靠解析 SQL，Redis 靠查命令表：GET → 只读 → 放行
4. 二级分流       → vm-docker-redis → RedisPlugin 实例
5. 插件执行       → redis-py 执行 GET
6. 写审计日志     → 记录命令原文
7. 返回

# AI 收到——Redis 的标量结果也规整为二维表（kind="table"）
{
  "ok": true,
  "kind": "table",
  "columns": ["value"],
  "rows": [["{\"uid\":10086,\"name\":\"张三\"}"]],
  "row_count": 1,
  "elapsed_ms": 2
}

场景 D · AI 想在 5.7 上用 8.0 的语法（明确报错，不悄悄改写）

# AI 发起——CTE 是 MySQL 8.0 才有的特性
db_query(connection="crm-prod", operation="WITH t AS (SELECT ...) SELECT * FROM t")

# 底座内部做的事
1. 分级判定       → 只读，放行
2. 二级分流       → MySQLPlugin 实例
3. 插件执行前检查 → 该连接探测到的是 5.7.43，不支持 CTE
4. 拒绝并说明   → 不执行，也不偷偷改写 SQL

# AI 收到
{
  "ok": false,
  "error": "该语法需要 MySQL 8.0 及以上，当前连接 crm-prod 的版本是 5.7.43",
  "suggestion": "可改用子查询，或在 local-test（8.0.44）上测试该语句"
}

为什么不自动改写 SQL？

因为改写有语义漂移风险——自动把 CTE 改成子查询，看着能跑，结果可能不一样。宁可挡住，也不给你一个悄悄出错的结果。

06配置怎么写

一类数据库一个文件，打开就是全部信息。

MySQL：三个环境在同一个文件里

# conf/mysqlConfig.yaml
# 顶层 key 就是连接别名，AI 说话时用的就是这个名字

local-test:
  host: 127.0.0.1
  user: root
  password: ${env:OMNI_MYSQL_LOCAL_PWD}
  database: testdb
  level: write              # 本地随便折腾

vm-docker:
  host: 192.168.56.10
  port: 13306               # Docker 映射端口通常不是 3306
  user: root
  password: ${env:OMNI_MYSQL_DOCKER_PWD}
  database: dev
  level: write

crm-prod:
  host: 10.20.30.40
  user: readonly            # 账号本身就是只读，双保险
  password: ${env:OMNI_MYSQL_CRM_PWD}
  database: crm
  level: readonly           # 生产锁死只读
  rules: [prod-safe]        # 挂上生产保护规则包

Redis 和 MongoDB

# conf/redisConfig.yaml
vm-docker-redis:
  host: 192.168.56.10
  port: 6379
  password: ${env:OMNI_REDIS_PWD}
  db: 0
  level: write
# conf/mongoConfig.yaml
vm-docker-mongo:
  host: 192.168.56.10
  port: 27017
  user: admin
  password: ${env:OMNI_MONGO_PWD}
  database: dev
  level: write

密码放在环境变量里

# .env —— 这个文件不进 Git
OMNI_MYSQL_LOCAL_PWD=your-local-password
OMNI_MYSQL_DOCKER_PWD=your-docker-password
OMNI_MYSQL_CRM_PWD=your-prod-password
OMNI_REDIS_PWD=your-redis-password
OMNI_MONGO_PWD=your-mongo-password

这样一来，conf/ 下的配置文件里没有一个真实密码，所以它们可以放心进 Git、也可以发给同事——他只要自己填 .env 就能连自己的库。

规则包：一套可复用的安全规则

# rules/prod-safe.yaml —— 建议按连接挂载；要全局生效可改 global: true
name: 生产保护
global: false             # 挂到需要的连接（如 crm-prod 的 rules: [prod-safe]）
max_level: readonly       # 最高只读
max_rows: 100             # 一次最多返回 100 行
deny:
  - DDL
  - multi_statement
  - update_without_where
# rules/dev-loose.yaml
name: 开发放宽
max_rows: 1000
deny:
  - multi_statement       # 只禁多语句，DDL 放开

规则是四层叠起来的

一条铁律：规则叠加只能往严里叠

规则项只能往哪调
max_level只能调低（readonly < write < danger）
max_rows只能调小
deny只能加，不能删

放宽只有两个口（v1.0 定稿语义）：连接内联的 level 是属主授权声明，直接生效（不写则默认 readonly）；规则包要放宽，必须在那个连接上显式写 unsafe: true。这样一来，以后你只要搜一次 unsafe 和 level，就能列出所有放宽点，审查极方便。

07AI 看到的工具

全部就 5 个，工具少，AI 才不容易选错。

工具干什么MySQL 示例Redis 示例
db_list_connections 有哪些库可用、什么级别、什么能力 不区分数据库类型
db_list_tables 列出有哪些表 / 集合 "testdb" 按 key 前缀分组
db_describe_table 看表结构 "testdb", "orders" key 的类型与 TTL
db_query 只读操作 "SELECT ..." "GET user:1"
db_exec 写入 / 结构变更（受级别管控） "INSERT ..." "SET k v"

AI 怎么知道每个库该传什么格式？

# db_list_connections 的返回里带上了这些信息
{
  "connections": [
    {
      "name": "crm-prod",
      "dialect": "mysql",
      "version": "5.7.43",
      "level": "readonly",
      "capabilities": ["sql", "entity", "describe", "transaction"],
      "operation_hint": "operation 传 SQL 字符串"
    },
    {
      "name": "vm-docker-redis",
      "dialect": "redis",
      "version": "7.2.4",
      "level": "write",
      "capabilities": ["command", "namespace"],
      "operation_hint": "operation 传 Redis 命令字符串，如 GET user:1"
    }
  ]
}

能力列表（capabilities）的作用在这里体现：AI 一看就知道 vm-docker-redis 没有 entity 能力，不会去调 db_list_tables。

08安全设计

三层防护：应用层拦截 + 规则收紧 + 数据库账号兜底。

三级权限

级别允许做什么默认
readonly 看库表结构、查数据 默认级别
write INSERT / UPDATE / DELETE 按连接开启
danger DROP / TRUNCATE / ALTER / 无 WHERE 的写 默认禁止

纵深防御：两道锁

层怎么做作用
应用层 解析操作语句，判断级别，超过连接上限就拦 挡住误操作
数据库层 连接账号本身用只读账号（user: readonly） 万一应用层被绕过，数据库也不让写

所以 crm-prod 的配置里有两处只读：连接级别写 readonly，账号也用只读账号。这不是冗余，是双保险。

分级判定怎么做

库判定方式举例
MySQL解析 SQL 结构（不靠字符串匹配，防绕过）SELECT → 只读；DROP → danger
Redis查命令名表GET → 只读；FLUSHALL → danger
MongoDB查方法名表find → 只读；dropDatabase → danger

Redis 有个特别坑的命令：KEYS *

它不是"慢"，是会把整个 Redis 实例卡死——所有客户端一起等。所以实现上双保险：判为 danger 并给出「改用 SCAN」的建议；且即使连接放开到 danger 级也不实际执行，返回空结果加提示。绝不自动改写 SQL/命令（语义漂移风险）。

09审计留痕

每次操作都记一笔，包括被拒绝的。

记录什么为什么
时间 · 连接名什么时候、在哪个库做的
操作原文到底做了什么
需要级别 · 实际级别是该放行还是被拦，一目了然
状态 · 耗时 · 影响行数成功、被拒、还是报错
错误信息失败原因

为什么要记「被拒绝的操作」

只记录执行成功的事，你只看到"AI 干了什么"；记上被拒的，你还能看到"AI 想干什么但被挡住了"。后者往往更有价值——它直接告诉你规则设得对不对、AI 是不是在乱试。

两个落点

落点用途
SQLite 数据库可查询、可统计（比如"这个月被拒了几次"）
JSONL 日志文件可直接看、方便外部工具采集

审计日志里含真实 SQL 语句，绝对不能进 Git。配置文件反而不怕（密码走了环境变量），日志才是真正敏感的东西。

依赖方向：一条线，绝不回环

解耦的真正判据

不是"分了模块"就叫解耦。插件只允许 from basePlugin import ...，绝不允许 import 底座内部任何东西。这条线守住了，插件才能独立测试、独立演进，底座改内部实现也影响不到它。

11能力范围

一条判定标准：能不能塞进「命名空间 → 实体 → 二维结果」这个模型。

档数据库类型
首版就做 MySQL 5.7 / 8.0（本地 / Docker / 云）· Redis · MongoDB
架构已就绪 PostgreSQL · SQLite · SQL Server · 国产库（达梦 / 金仓 / OceanBase / GaussDB）· Elasticsearch（可选）· ClickHouse（需超时兜底）
明确不做 时序（InfluxDB / Prometheus）· 图（Neo4j）· 向量（Milvus）· 异步数仓（Hive / Trino / BigQuery）

为什么不做后四类

它们返回的东西不是二维表——时序返回序列、图返回图、向量返回相似度、数仓是"提交-轮询"模型。硬塞进来要改结果结构和执行签名，会把整套契约拖成一团。这类库用专门的 MCP 工具更合适。

以后能往哪扩

想扩什么属于哪种怎么加
限流 / 配额切面挂在切面链上，不新增模块
敏感字段脱敏切面同上
元数据 / 结果缓存切面同上
两个环境结构对比模块 + 工具core/diff.py + db_diff 工具
SSH 隧道模块core/tunnel.py，插在连接层之下
危险操作二次确认模块 + 切面core/approval.py
查审计日志只要一个工具复用 audit.py，加个工具入口

注意最后一行——很多"新能力"根本不需要新模块，加个切面或加个工具就够。
